# The nf-tui name

The **code** is MIT licensed — take it, change it, ship it, sell it. See
[LICENSE](LICENSE).

The **name** is not part of that grant. MIT says nothing about trademarks
either way, which is why this file exists: so you don't have to guess where the
line is.

"nf-tui" identifies this project and who maintains it. The point of keeping it
distinct is not control over the software — you already have that — it's that
someone typing `nf-tui` should get this thing, and a bug report about "nf-tui"
should be about code that came from here.

## Yes, without asking

- Saying your tool works with, reads, wraps, extends or competes with nf-tui.
- Writing about it, teaching it, reviewing it, benchmarking it, criticising it.
- Redistributing it unmodified under its own name — packaging it for conda,
  Homebrew, Spack, a module system, your institution's software stack.
- Keeping the name in a fork you are not distributing, or in a pull request
  meant to come back here.
- Using the logo or screenshots in articles, talks and documentation.

## Ask first

- Naming a distributed fork, product or service `nf-tui`, or something close
  enough to be mistaken for it — `nf-tui-pro`, `nftui`, `NF TUI Enterprise`.
- Putting it in a company name, product name, domain or app-store listing.
- Anything that suggests this project endorses, maintains, sponsors or has
  reviewed your thing when it hasn't.

If you fork and distribute it, rename it. That is the whole ask, and it costs
you one line in a config file. Say it's *based on* nf-tui as loudly as you like
— that's accurate, useful to your users, and explicitly fine by the list above.

## Asking

Open an issue on <https://github.com/stavgrossfeld/nf-tui>. Permission is
usually easy to get; being asked is the part that matters.
