Debug a Nextflow run
from the terminal

nf-tui reads a run's log and work directories directly. It works on runs nobody set up for it — the one going now, the one a colleague launched, the one that failed in CI last Tuesday.

What it does

no instrumentation

Works on runs it never saw start

A platform has to be in the loop when the run launches. nf-tui reads what Nextflow already writes, so every historical run on your cluster is browsable today.

stays put

Nothing leaves your infrastructure

A local process reading local files. No run metadata, sample names or paths go anywhere. Under GxP, PHI or IP constraints that removes a review rather than starting one.

streams

A 10 GB output opens instantly

Every pane loads as you scroll — text, gzip, and BAM/CRAM decoded with samtools from the task's own container, mounts and all.

-resume

Resumed runs aren't empty

A resumed run logs only Cached process lines and no task handlers at all. Cached tasks are resolved against the work tree, so their logs, outputs and metrics stay browsable.

any executor

Local, SLURM, k8s, AWS Batch

All name their handler *TaskHandler, which is what the parser keys on. Cloud work trees are read through your own aws / gcloud — no SDK is added.

over ssh

Runs where the run is

Install it in your home directory on the login node. No daemon, no root, no service. Or serve the same UI to a browser and forward the port.

The one screen

Task tree, the selected task's log, its output files with sizes as they're written, the run log, and a squeue-style view of what's running versus queued. e jumps to the next failure and leads with why. 

# the whole run, as data
nf-tui --json /path/to/run

# only what broke
nf-tui --json --failed /path/to/run

# one object per line while it runs
nf-tui --json --watch 5 /path/to/run
KeyDoes
enext failure, and why it failed
ssort — slowest, then peak memory
dthe task's output files
t / ctask log / container log
prunning vs queued, with elapsed times
grun log, at the tail
Lopen any of it in less
/filter the tree, or search the log

For agents

nf-tui-mcp serves a run over MCP, so Claude or any MCP client can ask what broke. One call returns every failed task with the reason — not just the exit status. 

# wire it up
claude mcp add nf-tui -- nf-tui-mcp

# tools it exposes
list_runs     get_run      get_failures
get_task      list_outputs read_output
tail_log      search_log
// get_failures, from a real run
"exit": "137",
"why": "error during connect: Get
  \"http://…/docker.sock/_ping\": EOF",
"cause": "…terminated with an
  error exit status (1)"

Nextflow's own Caused by: line reports the exit status. The reason is what the command printed — here, the container runtime had died. An agent reading only the exit status would have gone looking for a bug in the pipeline.

Install

# with uv
uv tool install git+https://github.com/stavgrossfeld/nf-tui

# or pip
pip install git+https://github.com/stavgrossfeld/nf-tui
# point it at a run
nf-tui /path/to/run

# or launch one and watch it live
nf-tui nextflow run nf-core/sarek \
  -profile test,docker --outdir results

Python ≥ 3.10 is the only requirement. A container engine is needed for viewing BAM/CRAM and nothing else. Puts nf-tui, nf-tui-web, nf-tui-run and nf-tui-mcp on your PATH.

What hasn't been tested

Parsing and container-command construction are pinned by tests built from Nextflow's own output, and the Singularity path is executed against a shim that behaves like the CLI. But nothing here has run against a live scheduler, a real .sif, or a real S3 bucket — the cloud path is exercised through a fake aws. Reports from a real cluster are welcome.
